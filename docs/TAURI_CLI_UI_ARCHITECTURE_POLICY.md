# C2C Desktop — CLI/UI 실행 책임 및 공통 새로고침 정책

> 결정일: 2026-11-13 · 상태: **공통 구현 기준(신규·수정 코드에 우선 적용)**
>
> 이 문서가 Tauri 화면별 초기 구현안, 과거 WinForms 호환 계획, 성능 개선 실험과 충돌하면 **이 문서의 책임 경계**를 우선한다. 기존 구현이 이 정책에 맞는다는 뜻은 아니다. 이행 상태는 아래에 구분한다.

## 1. 제품 구조와 단일 책임

**C2C CLI가 백엔드이자 기능 실행의 단일 진실 공급원(Single Source of Truth)** 이고, **Tauri/React는 CLI의 프론트엔드**다. 독립 터미널에서 쓰는 CLI와 GUI는 같은 기능 구현·결과·보호 장치를 이용한다.

| 계층 | 소유하는 책임 | 소유하지 않는 책임 |
| --- | --- | --- |
| React 화면 | 사용자 입력/선택, 명령 호출 의도 전달, 표시·로딩·오류·결과/실행 기록, 부작용 안내·확인 UX | CLI 의미 해석, 설정 파일 직접 조회·수정, PID/포트/Health/권한·소유권 판정, 별도 CLI 결과 생성 |
| 앱 공통 상태/갱신 코디네이터 | 현재 화면별 갱신 대상 결정, 요청 중복 제거·취소/무효화, 진행 상태 표시, 공유된 CLI 응답의 화면 반영 | 각 화면에 존재하지 않는 새로운 백엔드 규칙, 임의의 2차 조회, CLI 검증 로직 재구현 |
| Tauri 어댑터(Rust) | UI IPC → 검증된 CLI 호출 연결, 프로세스 수명/실행 파일 출처 보안, 실행 환경·인자 전달, stdout/stderr 처리 및 제한, 오류·타이밍 전달; 앱 고유 OS 동작(창/트레이/자동 시작) | 별도의 명령별 상태 머신, 자체 config/repository/profile/job 파서, MCP 런타임 소유권·정상성 판정, CLI를 대신하는 명령 구현 |
| C2C CLI/공유 코어 | 명령 문법·인자·유효성 검사, 인증·권한·PID/프로세스 소유권·포트·Health, 프로젝트/프로필/작업 조회와 변경, 서버·터널 start/stop/restart/reload, 안전한 종료 확인, 출력 형식·오류 규약 | GUI 전용 화면 배치·트레이 표시 |

**원칙:** UI나 Rust가 독자적으로 같은 상태를 재계산하지 않는다. UI는 CLI의 구조화된 결과만 반영한다. 표시용 형식 변환, 입력창의 즉시 반응, 버튼 활성화, 명시적 확인창은 허용하되 **최종 검증·실행 권한은 CLI**에 있다.

### Tauri가 맡을 수 있는 예외

창 최소화/X/트레이로 숨기기·복원, Windows 로그인 자동 시작과 같은 **앱 자체의 OS 기능**은 Tauri 책임이다. 그러나 완전 종료가 MCP/터널을 중지해야 하면, Tauri는 **CLI의 중지 결과가 확정된 후** 앱을 종료해야 한다. 독립적인 Rust PID 종료·Health 판정·인스턴스 기록 삭제로 대체하지 않는다.

Tauri에 필요한 실행 파일 무결성 검사, 허용 인자 전달, 프로세스 생성·출력 크기 제한은 **브리지 보안**이며 CLI 도메인 기능을 재구현하기 위한 수단이 아니다. 이 브리지 보안도 **CLI 명령마다 불필요하게 중복 실행하지 않도록** 설계한다.

## 2. 실행 API와 검증 계약

1. 화면의 버튼과 CLI 콘솔은 동일한 CLI 기능 경로를 사용한다. 버튼식 명령과 직접 입력한 명령 사이에 기능·인증·성능 차이를 만들지 않는다.
2. CLI에 직접 전달할 수 있는 명령/구조화된 API를 명확히 정의한다. 쉘 명령 문자열을 CMD/PowerShell에 전달하지 않으며, 프로세스는 직접 실행한다.
3. **문법 검사**는 CLI가 제공하는 검증 기능 또는 CLI와 코드가 공유된 파서를 호출한다. 화면이나 Tauri가 허용 명령·옵션·값 검사 규칙을 또 작성하지 않는다. 단순 UI 입력 제한은 도메인 검증이 아니다.
4. **실행 시 검증**은 항상 CLI에서 다시 수행한다. UI가 미리 문법 검사를 표시하거나 사용자 확인을 받았다고 해서 CLI 보호 장치를 우회할 수 없다.
5. UI의 상태 변경 확인창은 작업 의도를 확인하는 UX이고, 실제 인증·소유권·상태 전제조건 검사는 CLI가 책임진다.
6. CLI 명령의 결과/오류는 구조화된 단일 응답 계약을 사용한다. UI는 필요 없는 추가 `status`/`config show` 호출로 성공 여부를 재판정하지 않는다.
7. 프로젝트·프로필 파일과 런타임 기록에 대한 정규화/버전/형식 검사는 **CLI 또는 CLI 공유 라이브러리 한 곳**에서 관리한다.

## 3. 실행 시간 정책 — '터미널 CLI와 거의 동일'

동일한 번들/버전, 동일한 명령·옵션·인스턴스, 동일한 격리 HOME/환경 변수·작업 디렉터리·서버 상태에서 **터미널 CLI와 GUI 호출을 비교**한다.

`GUI 총 시간 = UI 입력·IPC + 어댑터 처리 + CLI 자체 실행 + 결과 전달·표시`

- **최적화 대상은 GUI가 추가하는 오버헤드**다. UI 요청 한 번에 여러 Node CLI 사전 조회, 별도 Rust 상태/설정 검사, 독립된 Health/PID 점검, 직렬 중복 실행이 숨어 들어가면 안 된다.
- 데이터 조회(프로젝트·프로필·작업)와 상태 확인이 느리다면 **CLI 내부**를 측정·최적화하거나, CLI가 소유하는 장수 프로세스/공유 서비스·캐시를 설계한다. GUI만 빠른 직접 파일 조회를 만드는 방식은 금지한다.
- 캐시는 CLI 또는 공유 코어가 결과 유효성과 무효화 시점을 정의한다. UI 공통 상태는 **동일 응답의 중복 요청만 병합하거나 짧게 재사용**할 수 있고 도메인 데이터를 독자적으로 재계산하지 않는다.
- 읽기 전용 명령은 불필요한 사전 변경 명령·전체 파일 해시 재실행·복수 프로세스 기동을 요구하지 않는다. 꼭 필요한 실행 출처 검증은 캐시 무효화·배포 버전·파일 변경 등 근거 있는 경계에서 보장한다.
- 프로세스 생성 비용이 병목이면 CLI 쪽 실행 경로를 개선한다. 명령 이름에 따라 UI가 다른 백엔드를 대신 호출하는 임시 우회는 정식 구조로 채택하지 않는다.
- 계측은 **CLI 수행 시간 / 어댑터 추가 시간 / UI 전체 시간**을 분리한다. 정상·비정상, 첫 실행·반복, 서버 시작·중지·공개 터널 상태별로 측정한다.
- 수용 기준: 동일 조건에서 GUI 시간은 터미널 CLI 시간에 **의미 있는 추가 지연이 없어야 한다**. 초과가 발생하면 원인을 명시하고 GUI 오버헤드를 제거한다. 특정 절대 시간·배수를 사전에 성공으로 주장하지 않는다.

## 4. 전 화면 공통 새로고침 정책

**상단바의 단일 `현재 화면 새로고침` 버튼**이 수동 갱신의 유일한 진입점이다. 대시보드·프로젝트·실행 환경·작업·연결·진단·설정에서 동일한 위치, 동일한 로딩/비활성화/오류 표현을 쓴다.

1. **갱신 범위는 현재 화면**이다. 다른 화면 데이터를 무조건 함께 새로 읽지 않는다. 대시보드처럼 여러 종류를 실제로 보여주는 경우만 필요한 공통 조회를 합친다.
2. 조회 함수·중복 요청 병합·캐시 무효화·공유 상태 반영은 **앱 공통 갱신 코디네이터**가 담당한다. 하위 화면은 데이터·상태·화면별 갱신 완료 신호를 받아 표시한다.
3. 한 번 누르면 그 화면의 필요한 최신 데이터를 조회한다. 요청 중 재클릭은 중복 실행하지 않으며, 오래된 응답이 새 상태를 덮지 않도록 한다.
4. 화면 진입 시 초기 조회, 기존의 자동 주기·포커스 갱신 정책은 **기본적으로 유지**하되 수동 버튼과 요청이 겹치면 하나로 합친다. 무관한 화면을 동시에 조회하지 않는다.
5. 사용자 작업으로 데이터가 변경되면 CLI가 성공/변경 범위를 반환하고, 공통 상태는 **영향받는 화면만 무효화**한다. 작업 직후 무조건 전체 새로고침하지 않는다.
6. 각 화면의 **일반 새로고침/상태 확인 버튼은 상단바로 이관**한다. 다만 `Doctor 실행`, `잠금 목록 조회`, `서버 시작`, `로그 가져오기` 등 **명확히 구분되는 기능 실행 버튼**은 별개다. 이를 '새로고침'이라는 이름으로 중복 제공하지 않는다.
7. CLI 콘솔의 상단바 갱신은 **마지막 읽기 전용 실행 결과 재조회 또는 표시 데이터 갱신**만 가능하다. `stop`, `restart`, `config set`, `job cancel` 등 부작용 명령은 절대 재실행하지 않는다.
8. 새로고침은 읽기만 한다. 실패 시 기존 화면 상태/오류를 명확히 보여주며, 실패를 성공으로 가장하거나 서버를 자동 재시작하지 않는다.

## 5. 종료·트레이 정책과 지연

- 최소화 버튼: **창만 최소화**, MCP 상태 변화 없음.
- X 버튼 및 **트레이로 숨기기**: 창을 트레이로 숨기고 **서버·터널 유지**.
- 트레이 우클릭: **창 열기 / 종료**.
- **종료(완전 종료)**: CLI에 전용 인스턴스의 정상 종료를 한 번 요청하고 CLI가 소유권 확인·서버/터널 중지·포트/기록 정리 결과를 확정한다. 성공 시에만 Tauri 앱과 트레이를 종료한다. 실패하면 UI를 유지하고 오류를 표시한다.
- 종료 지연은 `CLI stop` 내부의 PID/프로세스 검증·시그널·종료 대기·터널 정리와, 브리지/앱 후처리로 분리 측정한다. **같은 소유권·포트·기록을 Tauri가 또 반복 검사하여 시간을 더하지 않는다**.
- 원인을 확인하기 전 임의 타임아웃 축소, 외부 PID 강제 종료, 작업 중단 성공 가장하기는 하지 않는다.

## 6. 테스트 및 수용 게이트

- **동등성:** `status`, `health`, `repository/profile/job list`, `stop`, `restart` 등 CLI 직접 실행과 GUI 결과/오류/실제 상태가 일치한다.
- **측정:** 위 동일 환경에서 각 명령 5회 이상 비교. 첫 실행과 반복 P50/P95 또는 개별 측정값 기록. GUI 추가 오버헤드를 단계별 계측한다.
- **소유권:** 다른 인스턴스·외부 프로세스·오류 기록에 대한 보호가 CLI 직접 실행과 동일하다.
- **새로고침:** 상단바 한 곳, 현재 화면만 조회, 요청 중 중복 방지, 자동/포커스 갱신 유지, 실패·이전 결과 처리, 상태 변경 후 관련 데이터만 무효화.
- **종료:** X/트레이 숨김은 MCP 유지, 트레이 종료/설정 종료는 동일 CLI 중지 경로, 지연 단계 기록, 실패 시 앱 유지.
- **회귀:** 기존 Windows Preview 수동 검수 기능(8개 화면) 및 자동 테스트 유지. UI 새 정책에 맞지 않는 소스 기반 테스트는 정책에 맞춰 함께 수정한다.

## 7. 기존 구현과 충돌하는 부분 — 정리 대상

이 문서는 **정책 확정**이며 아래 내용은 **아직 정리·교체 전**이다.

- Draft PR #103의 Rust `native_console_status` 및 자체 로컬 Health/PID 검사: **CLI 대신 상태를 판정**하므로 최종 구조와 충돌. 알고리즘 최적화와 Health 조기 반환의 실험·성능 측정은 자료로 남기되 **CLI 코어로 이전하거나 제거**해야 한다.
- 현 작업 브랜치 `perf/tauri-unified-refresh-and-lifecycle`의 Rust `catalog.rs` 직접 `repositories.json/profiles.json` 조회: **CLI 밖에 도메인 파서가 하나 더 생김**. 배포·병합 전 철회하고 CLI/공유 코어 최적화로 재설계한다.
- 현 작업 브랜치의 React `refreshManagedStatus`에서 `alive/healthy/port/tunnelRunning` 조합으로 런타임 상태를 재판정하는 로직: UI는 CLI의 **정규 상태 응답**만 반영하도록 대체한다.
- 현재 `run_owned_cli_parity`, `run_owned_cli_console`, `manage_owned_cli`, `inspect_owned_catalog` 등 복수 브리지는 성능과 역할 중복을 조사해 CLI 계약에 맞는 **단일 호출 계층**으로 정리한다. Rust는 IPC/안전 실행 어댑터 역할만 수행한다.
- 기존 화면별 새로고침 버튼은 제거하고 상단바로 통일하되, 해당 작업 브랜치는 **현재 미완성·미검증**이므로 곧바로 병합하지 않는다.
- 기존 문서의 WinForms 병행·18797 포트·모니터 전용 포트·별도 OS 상태 조회 설명은 이전 설계 기록으로 취급한다. 현재 기본 포트는 **7979**, 설정에서 실제 서버 포트를 변경한다.

## 8. 권장 구현 순서
